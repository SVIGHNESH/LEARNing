Software testing is less a checklist than a vocabulary — a way to describe how, where, and why a system might fail. What follows is a catalogue of that vocabulary, organised from the smallest unit of code to the broadest behaviours of a system in the wild.

Levels Methods Functional Non-Functional Maintenance · Modern
01Levels of scope

Testing Levels

Defined by how much of the system is exercised at once. The classic ladder, from a single function to a fully assembled product.

01 / 04Level

Unit Testing

The smallest piece of code — a function, method, or class — verified in isolation, usually with mocks or stubs replacing its collaborators.

  • JUnit · PyTest · Jest · NUnit
  • Owned by the developer
02 / 04Level

Integration Testing

Two or more modules or services exercised together to confirm their contracts hold at the seams.

  • Big-Bang · Top-Down · Bottom-Up · Sandwich
  • TestNG · REST-Assured
03 / 04Level

System Testing

The fully assembled application tested end-to-end against requirements — the first time it behaves as users will see it.

  • Black-box in nature
  • Owned by QA
04 / 04Level

Acceptance Testing

Validates that the system meets business intent and is fit for release. The final handshake before the ship leaves harbour.

  • UAT · BAT · Alpha · Beta
  • Contract · Regulation
02Lens of visibility

Testing Methods

Classified by how much knowledge the tester has of the code beneath the surface — three lenses, three philosophies.

01 / 03Method

Black-Box

Inputs in, outputs out. The internals are sealed. Tests written against specification, never against implementation.

  • Equivalence Partitioning
  • Boundary Value Analysis
  • Decision Tables · State Transition
02 / 03Method

White-Box

Source code is the map. Tests target paths, branches, and statements with surgical intent.

  • Statement · Branch · Path coverage
  • Loop & condition testing
  • Mutation testing
03 / 03Method

Grey-Box

The hybrid — partial sight of internals (a schema, an API) while still probing from the outside.

  • Matrix testing
  • Pattern testing
03What it does

Functional Testing

Does the software do what the spec says it should? Each technique below answers a different shade of that question.

01Functional

Smoke

The cursory "does it even start?" check after a new build lands.

02Functional

Sanity

A narrow, focused look after a small change — a rationality test.

03Functional

Regression

Re-runs the old suite to confirm nothing fresh has broken something old.

04Functional

Re-Testing

Re-executes a previously failing case after a fix to confirm the bug is gone.

05Functional

API

Endpoints, contracts, and data flow between services — tested without a UI in sight.

06Functional

UI / GUI

Layout, components, and the choreography of human interaction.

07Functional

L10n & G11n

Languages, currencies, dates, and the cultural assumptions baked into them.

08Functional

Ad-hoc & Exploratory

Unscripted, intuition-led — the kind that finds what no checklist anticipated.

04How well it does it

Non-Functional Testing

Speed, resilience, security, dignity. The qualities a user feels but rarely names.

01Non-Func

Performance

An umbrella for everything related to responsiveness and stability under workload.

  • Load — expected traffic
  • Stress — beyond limits
  • Spike — sudden bursts
  • Endurance — long duration
  • Scalability · Volume
02Non-Func

Security

Find the holes before someone less friendly does.

  • Penetration testing
  • Vulnerability scanning
  • Risk assessment · Ethical hacking
  • Posture & compliance
03Non-Func

Usability

Ease of use, learnability, satisfaction. Often a five-user study reveals more than a hundred bug tickets.

04Non-Func

Compatibility

Across browsers, operating systems, hardware, networks, and yesterday's versions.

05Non-Func

Reliability

The probability of failure-free operation over a defined window.

06Non-Func

Recovery

How gracefully the system rises after a crash, a power cut, or a region falling off the internet.

07Non-Func

Accessibility

WCAG, ARIA, screen readers — building for the full range of human ability.

08Non-Func

Installation

Install. Upgrade. Uninstall. The forgotten lifecycle, rediscovered the moment it goes wrong.

05After the change

Maintenance Testing

Performed on systems already in flight — after a patch, a migration, or an end-of-life.

01Maintenance

Confirmation

Confirms a defect's fix actually held, with no fresh casualties.

02Maintenance

Regression

The wider safety net after patches, upgrades, or platform changes.

03Maintenance

Migration

Validates data and behaviour when crossing between versions or platforms.

06Cross-cutting practice

Specialized & Modern Approaches

Approaches that ignore the categories above — they are practices, philosophies, and quiet revolutions.

01Modern

TDD

Failing test first, then code, then refactor. A discipline disguised as a workflow.

02Modern

BDD

Given / When / Then. Specifications written so that humans and machines can read the same sentence.

03Modern

ATDD

Acceptance criteria become the tests, written before a single line of production code.

04Modern

Mutation

Deliberately corrupts code to ask: would your tests have noticed?

05Modern

Fuzz

Random or malformed inputs at high speed. The favourite tool of the security researcher.

06Modern

Property-Based

Asserts invariants over generated input. QuickCheck, Hypothesis, and friends.

07Modern

Snapshot & Visual

Compares rendered output against a baseline — pixels, DOM, or otherwise.

08Modern

Contract

Producer/consumer agreements pinned down so microservices stop lying to each other. (See: Pact.)

09Modern

Chaos Engineering

Inject failure on purpose. Discover what the architecture diagram quietly omitted.

10Modern

A/B Testing

Two variants, real users, statistical truth. Less testing than experimentation.

11Modern

Shift-Left / Right

Push testing earlier into development — or later into production observability.

12Modern

Continuous

Tests woven into CI/CD so that every commit is a small, automatic referendum.

07The trade-off

Manual vs. Automated

Not opposing schools — complementary instruments. The art is in choosing which to deploy, and when.

Table 01 — Trade-offs between manual and automated approaches
AspectManual TestingAutomated Testing
Best forExploratory work, UX, ad-hoc investigationRegression, load, anything repetitive
SpeedSlow — bound to human paceFast — bound to CPU cycles
Initial costLow to set upHigh — frameworks, infra, training
Long-term costHigh — repeats every cycleLow — amortised across runs
ReliabilitySubject to human error and fatigueDeterministic, given stable inputs
ToolkitTest cases, checklists, intuitionSelenium, Cypress, Playwright, JUnit

End of compendium.

Quality is not the absence of bugs but the presence of confidence — and these methods, taken together, are how that confidence is built one assertion at a time.
